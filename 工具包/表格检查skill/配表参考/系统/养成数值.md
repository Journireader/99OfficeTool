## 1.1 代码确认的养成总链

```text
主养成表
  -> Attribute
  -> Condition / Skill
  -> Item / Random / Reward / Store
  -> I18N / Picture / Resource / Model / AVG
  -> 角色属性聚合
```

当前代码确认的关键点：

- 装备格强化会被服务端预处理成 `{装备部位, 强化等级} -> AttrData`；`AttrData` 必须和 `EquipGrid.Attr` 数量、顺序一致。
- 装备格基础属性、强化属性和共鸣属性会并入 `AFFIX_GROUP_EQUIP_GRID`。
- 时装在 battle-core 内按 `FashionID_Star`、`FashionID_Level`、`FashionID_Star_PrimaryProfessionType` 索引；套装下的 FashionID 列表来自 `FashionStar.SuitID`。
- 圣物属性分两层：`RelicPool` 生成圣痕属性，`RelicAltar` 提供祭坛属性；二者都会进入角色属性聚合。`RelicBase.IcePool / FirePool` 不是 SkillID。
- 黑猎人解锁走 `HunterList.ConditionID`；`HunterTalent.ConditionID` 是前置技巧配置 ID 列表，不是公共 Condition。

## 2. 当前表结构速查

### `role/PrimaryProfession.xlsx`

- `PrimaryProfession`：职业基础行。关键字段包括 `PrimaryProfessionID`、`Name`、`HeroModelID`、`ProfessionAffixs#N.*`、`ProfessionDes`、`ProfessionEquip`、`BasicAttr#N.Type/Data`。
- `PriProSkillBuild`：技能槽位 / Build 解锁。关键字段包括 `BuildType`、`BuildSerialNumber`、`UnlockLevel`、`ConditionID`、`SkillID`。

注意：

- `UnlockLevel` 是前端展示层级；`ConditionID` 是后端激活条件，两者都要校验。
- `SkillID` 可以是分号分隔数组，不是一格只放一个技能。
- 本轮 `PriProSkillBuild` 新增 `PassiveSkillID`，被动技与 `SkillID` 分列，不要塞进同一格。
- `ProfessionAffixs#N` 现在带 `affixName` 和 `affixBgColor` 两列，职业标签的文案与底色一起配。
- `PrimaryProfession` 新增 `PowerDiff`（初始战力差值），进阶属性位扩到 21 组，`OtherAttr` 收到 11 组（原 #12/#13 已移除，改前先确认没有行还在用）。
- 战力口径另有 `role/Attribute.xlsx#Attribute` 新增的 `StaticCombatPowerCoefficient`（玩家静态战力系数）。`PowerDiff` 管初始差值、系数管静态折算，两者分开，不要互相代入。

### `develop/Exp.xlsx`

- `KnightExp` / `WizardExp`：当前行列以 `约定/全表快照.md` 为准，不在本文登记。
- 关键字段：`ExpID`、`HeroUpgradeData`、`BasicAttrFirst#N.Type/Data`、`BasicAttrSecond#N.Type/Data`。
- 本轮两张表都新增 `ExpStoreMax`（经验池容量）和 `FatigueStoreMax`（活力可达上限），按等级逐行配。

字段说明明确写了 `BasicAttrFirst#N.*` “仅覆盖冒险玩法掉落装备”。因此它不是职业基础属性表，也不是所有装备模板的基础数值表。需要改职业初始面板时先看 `PrimaryProfession`；需要改装备模板范围时先看 `Equip`。

### `develop/Equip.xlsx`

- `Equip`：当前快照为 249 行，53 列；以源表实时内容为准。
- 关键字段：`EquipID`、`Name`、`PriProType`、`PartType`、`QualityType`、`AdvancedAttrNum`、`IconID`、`HeroEquipModelID`、`DropItemResID`、`BasicAttr#N.*`、`AdvancedAttr#N.*`。

本轮新增 `EquipLevel`（装备等级）。装备表同时承接职业、部位、品质、图标、模型、掉落展示、基础词条和进阶词条。改单件装备时通常还要核对 `事实卡/Equip_Attribute_Random.md`、`I18N#Equip`、`Picture`、`HeroEquipModel`。

### `develop/EquipGrid.xlsx`

- `KnightEquipGrid` / `WizardEquipGrid`：装备格初始属性和挂点。
- `KnightEquipReinforce` / `WizardEquipReinforce`：强化等级曲线。字段按 `EquipGrid#N.Type` + `EquipGrid#N.AttrData#M` 展开。
- `KnightEquipResonance` / `WizardEquipResonance`：共鸣等级属性和消耗。

注意：

- 骑士与巫师装备格均有 3 个初始属性槽；各部位 Attr 类型、顺序须与强化表的 3 个 AttrData 值一致。
- 强化表字段说明为“强化成功后覆盖 DB 数据”，不要把它理解成对上一强化等级的增量。客户端展示总属性时会把装备格初始属性与当前强化等级属性合并展示。
- 骑士强化属性类型以 `KnightEquipGrid` 的 `Attr#N.Type` 为准；`KnightEquipReinforce` 只填同顺序的覆盖值。按 0519 养成数据回填时，先同步 `KnightEquipGrid` 属性类型，再写 1-120 级强化值。
- 共鸣表以 `EquipResonanceID` 表示共鸣等级或门槛，备注列按等级写 `1级`、`2级`、`3级`、`4级`、`5级`。

### `develop/Adornment.xlsx`

- `AdornmentSkin`、`AdornmentHair`、`AdornmentFace`：肤色 / 发型 / 表情。
- `AdornmentClothes`：时装外观本体，主键 `AdornmentClothesID`。
- `FashionStar`：时装升星，`FashionID` 关联道具 / 外观。
- `FashionLevel`：时装升级，受 `NeedStar` 约束。
- `FashionSuit`：套装维度，`FashionID` 是套装 ID，不是单件道具 ID。

详细串联规则见 `系统/骑士时装.md`。维护时装时必须同步判断 `Item`、`I18N#AdornmentClothes`、`I18N#Item`、`I18N#Fashion`、`Condition`。

### `battle/Relic.xlsx`

- `RelicBase`：本体、部位、图标、冰 / 火痕属性池和套装技能。
- `RelicLevel`：等级经验、等级效果 Skill、等级效果描述和分解返还。
- `RelicStar`：星级消耗和分解返还。
- `RelicAltar`：圣火祭坛，全局等级属性，不接入 ECE。
- `RelicPool`：冰痕 / 火痕属性池，当前使用 `1001/1002`、`2001/2002`；预留段为冰痕 `1001-1099`、火痕 `2001-2099`。

重要修正：

- `RelicBase.IcePool` / `FirePool` 是属性池 ID，引用 `RelicPool.PoolID`，不是 SkillID。
- `RelicBase.ThreeIceID` / `ThreeFireID` / `TwoIceID` / `TwoFireID` 仍是套装效果 SkillID。
- `RelicLevel.Effect` 是等级效果 SkillID，`EffectDes` 落 `I18N#Relic`。
- `RelicAltar` 直接配 `Knight.*` / `Wizard.*` 属性。两组列对应 proto 里的 `AttrTypeData Knight` / `AttrTypeData Wizard` 结构体展开，按 `Knight.Type/Data`、`Wizard.Type/Data` 对称填写。
- `RelicLevel` 新增 `FireEffectID` / `IceEffectID`，火痕与冰痕技能改为分列配置，不再共用单一等级效果列。
- 新增 `RelicMark` sheet：按 `RelicID` 配圣痕，`MarkInfos#N` 给出圣痕类型、成长 ID 和 `Min/Max/Step`。随机结果下界与上界都必须是 `Step` 的整数倍，`(Max-Min)` 也要能被 `Step` 整除。

### `develop/BlackHunter.xlsx`

- `HunterList`：黑猎人本体。关键字段包括 `HunterID`、`Name`、`PictureID`、`KnightDescribe`、`WizardDescribe`、`TreeType`、`ConditionID`、`AvgID`。
- `HunterTalent`：技巧节点。ID 规则写在表头：`HunterID * 10000 + TalentID * 100 + TalentLevel`。
- `TreeType`：天赋树模板坐标，`TreeTypeID` + `TalentID` 决定节点位置。

黑猎人技巧有 Knight / Wizard 两套属性字段。新增或调整时要同时检查文案、图片、条件、AVG 入口和树模板坐标。

### 承接链路

- 装备奖励或掉落：先看 `事实卡/Equip_Attribute_Random.md` 和 `develop/Equip.xlsx`，再看 `random/Random.xlsx` 的装备品质 / 部位 / 属性随机池，最后看 `Item.xlsx#EquipChest` 是否通过箱子发放。
- 时装获得：先看 `AdornmentClothes` / `Item` / `Condition`，再看 `FashionStar` / `FashionLevel` 是否需要升星升级承接。
- 圣物获得：先区分圣物本体、等级效果、属性池和祭坛；奖励发放端还要确认是直接发圣物道具、箱子，还是活动奖励表间接发放。
- 黑猎人解锁：检查 `ConditionID`、`AvgID`、文案、图片和技巧树坐标。

只要养成内容通过奖励、商店、箱子或活动发放，就必须补查 `system/Item.xlsx`、`system/Store.xlsx`、`random/Random.xlsx`、`reward/*.xlsx` 或 `commerce/ActivitySchedule.xlsx` 的实际落点。

## 4. 配置习惯与隐含关系

这一节只记录“表怎么配进去、下次怎么更快联查”，不评价数值曲线。

### 等级经验

- `KnightExp` 和 `WizardExp` 都是按等级顺序铺行的等级表；不要把它当成按职业补几行的枚举表。
- `WizardExp` 当前存在引用 `KnightExp` 的公式列，例如基础属性数据从骑士表相邻单元格派生。复制或改写巫师经验表时，先检查公式依赖，不要只看最终数值。
- `BasicAttrFirst#N.*` 的字段说明限定为冒险掉落装备，不是职业初始面板；职业基础属性仍回 `role/PrimaryProfession.xlsx`。

### 活力（挂机产出闸门）

本轮新增，跨三张表，配的时候要一起看：

- `develop/Exp.xlsx#KnightExp/WizardExp` 的 `FatigueStoreMax`：该等级下活力能存到多少；`ExpStoreMax` 是经验池容量，两者分开。
- `adventure/OnlineAfk.xlsx#Fatigue`：按 `Level` 配 `FatigueLimit`（活力上限）。
- `adventure/OnlineAfk.xlsx#FatigueClear`：用资源换活力，`Resource.PropType/PropID` 指定消耗，`Resource.FatigueClear` 是增加量，`Order` 只管展示顺序。
- `adventure/OnlineAfk.xlsx#OnlineAfk` 新增 `AddFatigue`，是挂机产出对应的活力消耗。

注意字段名用 `Fatigue`（疲劳），表头中文写的是"活力"，同一个东西，不要当成两套数值。

### 装备与装备格

- `Equip` 是装备模板行，承接职业、部位、品质、图标、模型、掉落展示、基础词条和进阶词条；不是只配 `EquipID`。
- `EquipGrid` 的初始格、强化、共鸣分 sheet 配。强化字段说明是“强化成功后覆盖 DB 数据”，读法是覆盖值，不是增量加成。
- 骑士和巫师装备格均为 3 属性槽；巫师侧本轮补齐第 3 槽（`WizardEquipGrid.Attr#3.*`、`WizardEquipReinforce.EquipGrid#N.AttrData#3`），共鸣扩到 6 组（`WizardEquipResonance.ResonanceAttr#N.*`）。批量复制前仍须按 sheet 核对部位、属性类型和数值顺序。

### 时装

- `AdornmentClothesID` 是外观本体 ID；普通时装当前配置习惯通常与 `system/Item.xlsx#Item.ItemID` 共用同一段道具 ID。
- `FashionStar` 和 `FashionLevel` 不是单行配置；同一个 `FashionID` 会按星级、等级重复多行。抽样中 `FashionID=6020111` 在升星表有 6 行，在升级表有 12 行。
- 0519 养成数据的皮肤品质映射：`低级` 对 `[物品品质]史诗`，`中级` 对 `[物品品质]传奇`。`高级` 当前正式表无对应品质和 `FashionID/SuitID`，不要无 ID 盲增。
- `FashionStar.FashionID` / `FashionLevel.FashionID` 按时装道具 `ItemID` 关联。普通时装可沿用 `AdornmentClothesID = ItemID = FashionID` 的配置习惯；如果投放道具和外观本体分离，不要把这两张表的 `FashionID` 简化成 `AdornmentClothesID`。
- `FashionStar` 的 `Star=1` 行同时承担激活行；套装星级按同 `SuitID` 全部件拥有后的最低星级生效。
- `FashionStar.PassiveCondition/PassiveLimit/PassiveAttr` 是 r5008 新增的 Excel 结构，当前 proto 与非生成消费者未闭合；程序补齐前不能按已生效被动属性配表。
- `FashionSuit.FashionID` 是套装 ID，和单件 `AdornmentClothesID` 不是同一语义；单件通过 `SuitID` 指向套装。
- `AdornmentSkin` / `AdornmentFace` 等外观资源字段里可能有公式生成的资源路径或大写化规则，改资源字段前要保留公式意图。
- 养成表里的属性类型以 `role/Attribute.xlsx#Attribute` 为准；伤害结果提升类使用 `[属性类型]伤害结果提升`，受伤结果降低类使用 `[属性类型]受伤结果降低`，不要再使用旧的 `[属性类型]最终易伤` / `[属性类型]最终降伤`。

### 黑猎人

- `HunterTalent.ID` 的表头规则是 `HunterID * 10000 + TalentID * 100 + TalentLevel`；不要手填成无规律流水号。
- `TreeType` 是天赋树坐标模板。抽样中一个 `TreeTypeID` 会重复多行承接多个节点坐标，改技巧节点时要同时确认树模板。

### 圣物

- `RelicPool` 承接圣痕属性池。0519 养成数据按 `火/冰-1/2/3` 给到每池 9 个属性项，正式表已扩到 `Attr#9`。
- 池 ID 口径：誓印冰痕 `1001`，战刃冰痕 `1002`，誓印火痕 `2001`，战刃火痕 `2002`。
- 圣痕属性名按数值表原文落入 `Attr#N.Type`，不要强行改写成旧的基础属性枚举名。
- `HunterTalent` 同时有 Knight / Wizard 两套属性字段，新增或调整技巧时要双职业同时检查。

### 道具、箱子和随机池承接

- 养成物品经常不是从养成主表直接发放，而是先落到 `Item`，再被箱子、随机池、活动、商店引用。
- `ChestID`、`RandomID`、`DropItemRandomID` 这类字段常见读法是“同 ID 多行组成一组”，不是一行代表一个完整奖励。
- 装备箱、随机箱、自选箱的字段语义不同；发箱子时先确认箱子类型，再解释 `Reward#N.*` 或权重字段。

### 军团科技图标引用

- `system/Guilds.xlsx#GuildTechnology.Icon` 填 `system/Picture.xlsx#Picture.PictureID`，不填图片文件名或完整资源路径；字段名仍为 `Icon`。
- 前端 `UIGuildTechSkillItem` 通过 `ConfigModule.getPictureFileName` 读取 `FileName`，再按 `PathConfig.Img_BuffIcon` 加载 `textures/icon/buffIcon/<FileName>`。当前图标取自既有 Buff 图集，引用的图片必须存在于该目录。
- 空或无效 PictureID 不发起图片加载并清空旧图标。图标改动不影响科技名称、描述、属性、消耗及解锁条件；名称和描述仍由 `I18N#GuildTechnology` 提供。

## 5. 配置检查项

- 先确认改的是模板值、等级曲线、强化覆盖值、共鸣门槛，还是显示文案。
- 属性字段统一核对 `role/Attribute.xlsx`，不要凭中文名手填。
- 涉及玩家可见名称 / 描述时同步检查 I18N sheet 归属。
- 涉及解锁时同时检查 `UnlockLevel` 和 `ConditionID`。
- 涉及道具获得、消耗、分解返还时同步检查 `Item` 和数量字段。
- 涉及箱子、活动或商店发放时同步检查承接链路，不要只改养成主表。
- 涉及圣物时先区分属性池、等级 Skill、套装 Skill、祭坛属性，避免把 `IcePool` / `FirePool` 当成技能 ID。
