### 当前基线与使用门禁

- 在线字典 revision 4693：Event 共 24 个编号（100～123，其中 115 注销、119 参数未维护）；Condition 共 22 个公开编号；Effect 共 103 个数字行（其中 601 为空壳、50003 待开发、80001 已注销）。

## §1 先选入口，再配 ECE

战斗配置不是一律从 Event 开始。先判断效果由谁执行：

| 需求形态 | 默认载体 | 入口 | 生命周期责任 |
|---|---|---|---|
| 当前主动技能在某个表现帧立即执行 | 主动 Skill | `SkillDirector.LogicalTrigger#N.SkillEffects` | Skill 本次释放 |
| 长期监听命中、受击、释放、Buff 增减等事件 | 被动 Skill | 行级 `Skill.CastEventID` | 被动 Skill |
| 持续时间、层数、周期、临时监听、结束撤销 | Buff | `Effects#N.EventID`；空值为激活立即执行 | Buff |

一次性结果优先放当前 Skill；长期事件监听用被动 Skill；持续状态用 Buff。被动可以用 Effect 201/202 添加 Buff。结果等价时选择表更少、链路更短、生命周期责任最清楚的方案。

选好入口后，再组合：

```text
入口 → Event（如需要）→ Condition（如需要）→ Chance（如需要）
     → Target（最终作用对象）→ Effect（执行什么）
```

Condition 只判断，不执行动作；Effect 只执行结果，不代替事件过滤。主动 Skill 的 Effect 槽虽保留 `EventID` 列，但当前运行不读取，默认必须留空。

### §1.1 Skill 与 Buff 的真实字段

| 载体 | 效果槽 | 事件字段 | 每槽字段 |
|---|---:|---|---|
| Skill | 6 | 被动入口只读行级 `CastEventID` | `ConditionID / ChanceType / ChanceID / TypeID / TypeData / TargetType` |
| Buff | 5 | 每槽独立 `Effects#N.EventID` | `ConditionID / ChanceType / ChanceID / TypeID / TypeData / TargetType` |

当前 Excel 结构：

- Skill 的 #1～#5 有 `ChanceType + ChanceID`，#6 只有 `ChanceID`，没有 `ChanceType`。
- Buff 当前只展开 `Effects#1.TargetType`；#2～#5 对应 proto 字段同样存在。需要时打开精确的 `Effects#N.TargetType` 列，不要因此拆 Buff。
- `TargetTypeData` 虽在 proto 中存在，但当前运行链未消费，默认不开列、不填写。
- Buff Effect 的 EventID 为空不是断链：激活时立即执行；只有需要事件驱动时才填 Event 实例。

### §1.2 被动 Skill 的落位

```text
UseType = 被动
CastEventID = BattleEvent 实例（必填）
CastConditionID = 整条被动共用条件（按需）
CastChanceType / CastChanceID = 整条被动共用概率（按需）
Effects#N = 各效果自己的 Condition / Chance / Target / Type
Effects#N.EventID = 空
```

- 整条被动共同判断放 Cast 层；只有某个 Effect 独有的判断放该 Effect 层。两层可同时使用，执行顺序是 Cast 条件/概率先过，再逐 Effect 判断。
- 一个被动只能有一个行级 Event。需要监听多个 Event 时拆成多条被动 Skill。
- 主动通过 Effect 101 释放一个 helper Skill 时，helper 若按事件监听工作，仍按被动 Skill 配完整 CastEventID/Condition。

### §1.3 概率：填 ProbabilityID，不直接填万分比

`CastChanceID` 和 `Effects#N.ChanceID` 引用 `Probability.xlsx.ProbabilityID`。概率值写在 Probability 表，不直接写入 Skill/Buff。

| 需求 | ChanceType | ChanceID |
|---|---|---|
| 必定触发 | 空 | 空 |
| 固定概率 | 空 | ProbabilityID |
| 累积概率 | `[概率类型]累积概率` | ProbabilityID |

规则：

- 一个独立概率机制默认新增 ProbabilityID；只有明确要求共用同一平衡值或 Effect 1901 修改同一概率时才复用。
- 新增前查重；同一概率值不代表同一机制，不能仅因数值相同就共用。
- 只有整条被动累计时放 Cast 层；若仅一个 Effect 累计，拆成独立被动 Skill，避免其他效果被同一累计门控。
- 如果 100% 概率必须进入 Event 123 / Effect 1901 链，使用独立 ProbabilityID 且 Probability=10000；普通必定触发直接留空。

### §1.4 两套 TargetType 不能互抄

Skill Effect：

| 值 | 含义 |
|---:|---|
| 100 | 施法者自身 |
| 200 | 本次搜索得到的全部目标 |
| 300 | 本次搜索结果的第一个主目标 |

Buff Effect：

| 值 | 含义 |
|---:|---|
| 0 / 10 | Buff 持有者 |
| 20 | Buff 施法者 |
| 30 | 本次 Event 的目标；无事件目标时回退持有者 |

`Skill.SearchTargetType` 先产生候选目标，Effect.TargetType 再决定最终落点。当前搜索枚举包括：`100己方 / 101自身 / 102友方 / 200敌方 / 201敌方玩家 / 202敌方怪物 / 300全体`。不要把 SearchTargetType 的 100/200 与 Effect.TargetType 当成同一套枚举。

TypeData 内若还有“取值目标、统计目标、锚点目标”，只决定公式从谁身上取数或以谁为锚点；最终谁受到 Effect 仍由通用 TargetType 决定。

### §1.5 Event 与 Condition 使用实例 ID

| 类型 | 实例表 | 引用位置 |
|---|---|---|
| Event | `develop/battle/BattleEvent.xlsx` | `Skill.CastEventID` 或 `Buff.Effects#N.EventID` |
| Condition | `develop/battle/BattleCondition.xlsx` | CastConditionID 或 Effects#N.ConditionID |

当前 BattleEvent 实际有 102 条非空实例，物理数据到第 104 行；旧 Table/UsedRange 只到第 95 行，读取时必须看真实非空单元格。ID 末位是实例流水号，不是参数位。

- Event：完全相同的类型、关系、细类、参数才复用；找不到合适实例时新增。
- Condition：逻辑类型、ConditionType、参数和顺序完全相同才复用。预计会独立维护或以后分化时新增，禁止修改共享 Condition 迁就新需求。

### §1.6 执行顺序与事件粒度

- 主动 Skill 按 `SkillDirector.LogicalTrigger#N.SkillEffects` 中的槽序执行；`2;3;1` 就是 Eff2 → Eff3 → Eff1。
- `SkillEffects` 是 1-based 槽序，不是 Effect TypeID。
- 攻击生效 116/117 是 Trigger 生效粒度；造成/受到伤害 102/101 是实际伤害实例粒度。
- Event 的“前/后”是结算节点，不是延迟。多段技能会按每段伤害派发，不代表整次技能已经结束。
- 需求若指定最后一击或第 N 段，直接挂到对应 LogicalTrigger；不要用整次技能事件猜关键帧。
- 需要逐目标读取血量、护盾或注入本次伤害修正时，使用伤害实例粒度的 Event，不用 Trigger 粒度代替。

### §1.7 配表最短路径

1. 把需求拆成“何时、谁满足什么、以多大概率、对谁、做什么、持续多久”。
2. 选主动 Skill / 被动 Skill / Buff 入口。
3. 查现有 Event、Condition、Probability、Buff 是否可精确复用。
4. 按本文 §2～§4 填 TargetType、Effect TypeData 与 Buff 生命周期。
5. 主动回查 Director；被动回查业务主表是否引用；Buff 回查添加来源和移除/刷新路径。
6. 按 §6 完整校验，不以“引用存在”代替语义验收。

## §2 Event / Condition / Effect 全量速查

标记说明：

- `可用`：revision 4693 有公开定义，当前客户端有同号枚举和注册处理器；仍须按具体载体、上下文和参数验收。
- `冲突`：字典、Excel、proto 或当前实现对编号、单位、参数或结果有明确分歧；禁止静默选边。
- `未开放`：在线行为空、待开发、已注销，或当前客户端缺同号枚举／处理器；不得用于新配置。
- “有枚举 + 有 Handler”只证明执行入口存在，不证明公式、时序和边界已被运行实测。

| 8001 | Buff剩余时间 | `目标关系,1持有/2不持有,BuffID,时间比较方式,毫秒` |

组合规则：

- 一条 BattleCondition 的 `LogicalType` 只能统一 AND 或 OR；当前 Excel 展开 4 个 ConditionItem。
- 同时需要 `(A AND B) OR (C AND D)` 时，新建子 Condition，再用 Type 99 引用，禁止拆成多个可能重复触发的被动 Skill。
- ConditionID 必须唯一，所有引用必须存在。空 ConditionItems 当前视为 true，但新配置不要用空条件表达业务规则。

### §2.3 Effect 通用规则

- TypeData 必须逐位对应本节；同类旧配置可能本身错误，不能只复制相邻行。
- 单位优先写明：时间默认毫秒；概率/比例默认万分比，`10000=100%`；权重只做相对比较时不要求合计10000。
- TargetType 只决定最终作用对象；公式中的取值目标、Buff统计目标、传送锚点不替代 TargetType。
- `0`、空值、缺省值是否等价取决于具体 Effect，不能统一理解为“忽略”。
- 同一 TypeID 在 Skill 与 Buff 两条管线可能参数数目或生命周期不同；有差异时以下表为准。

### §2.4 状态、Trigger、技能修正 Effect

## §3 Buff 生命周期与重复添加

重复添加规则的直接控制项是 `StackConfig.Rule`，不是 `BuffEffectType`。但当前 `Buff.xlsx` 物理列只展开了 `StackConfig.MaxStack`；proto 里虽还有 `Rule` 等字段，运行时当前只消费 `Rule / MaxStack`。因此配表时必须区分“当前表可填字段”和“协议有但当前表未开放字段”。

### §3.1 当前可配范围与默认规则

当前源表没有 `StackConfig.Rule` 列时，运行时会按 `BuffEffectType + MaxStack` 推导默认规则：

| BuffEffectType | 名称 | 当前默认重复添加规则 |
|---|---|---|
| 100 | 护盾 | `REPLACE` |
| 200 | 属性增益 | `MaxStack>1` 时 `STACK_REFRESH`，否则 `REPLACE` |
| 300 | 持续治疗 | `REFRESH` |
| 400 | 控制 / 异常 | `IGNORE` |
| 500 | 属性减益 | `MaxStack>1` 时 `STACK_REFRESH`，否则 `REPLACE` |
| 600 | 持续伤害 | `REFRESH` |
| 700 | 定时 / 机制类 | `STACK_NO_REFRESH` |

`BuffEffectType` 在这里是默认规则的输入之一，不是完整叠加配置。需求若必须使用非默认 Rule，不要虚构列或把 Rule 塞进别的字段；先确认是否允许在源表开放精确的 `StackConfig.Rule` 列。

协议枚举：`0初始 / 1刷新 / 2叠层 / 3顶替 / 4忽略 / 5叠层并刷新 / 6叠层不刷新 / 7独立实例 / 8仅满层刷新 / 9累计`。当前未开放 Rule 列不等于这些枚举都能直接落表。

### §3.2 同来源与不同来源

- 同来源、同 BuffID：按最终解析出的 Rule 处理。
- 不同来源、同 BuffID：控制 / 异常类会拒绝；其他类型当前按独立实例共存。
- 普通多层 Buff 的多个 stack 仍是一个 Buff 实例；只有独立实例规则或不同来源实例才分别计数。Effect 402/403 统计的是活跃 Buff 实例数，Effect 401/501 才读取层数。

### §3.3 Effect 201 的添加层数

Effect 201 TypeData 为 `BuffID,层数方法,系数`：

| 层数方法,系数 | 含义 |
|---|---|
| `0,0` | 不指定新增层数，交给 Buff 自身规则处理 |
| `1,1` | 固定添加 1 层 |
| `1,N` | 固定添加 N 层 |
| `2,N` | 随机添加 1～N 层 |

层数参数只回答“本次加几层”，不会替代 MaxStack、Rule 或持续时间规则。Effect 202 的固定系数必须显式 `>=1`，不能依赖201的兜底。

### §3.4 Buff Effect 的执行时机

- `Effects#N.EventID` 为空：Buff 激活后立即执行该 Effect；不要误填一个无意义 Event。
- `Effects#N.EventID` 非空：在 Buff 生命周期内订阅对应 Event，命中后再执行 Condition → Chance → Effect。
- `BUFF添加/移除` 回调判断“本次是哪一个 Buff”用 Condition 1000；判断“目标当前是否持有 Buff”用1001。两者不能互换。
- Buff 添加/移除事件的当前对象已经是该 Buff 所在单位；继续判断它自身状态通常用关系 `1=自身`，不要因需求写了“敌方身上的 Buff”就机械填 `20=敌方`。
- Effect 12001 只在该 Buff 自然到期时结算同一 Buff 内的寄存伤害；持续时间取 `Buff.DurationData`，TypeData `0,0` 作为兼容占位。驱散、顶替、手动移除等非自然移除不结算。

### §4.1 爆发铭文实战补充

爆发铭文常见需求会同时碰主动替换、范围生成、Buff 叠层、寄存结算和 CD 调整。优先按下面口径拆，避免把复杂逻辑硬塞进一条主动 Skill：

- **Effect 101 调 helper 要先看 UseType**：主动 helper 被释放后立即按自身 Director 执行，不填 CastEvent；被动 helper 是挂载监听器，必须配 `CastEventID`，再按需用 `CastConditionID` 限定来源。两条分支不能混写。
- **爆发免控放 0 帧瞬时**：爆发主动需要免疫控制时，在 Skill 增加 `免疫控制` 效果，并在对应 `SkillDirector` 增加 `CreateTime=0`、`Type=瞬时` 的 `LogicalTrigger` 命中该效果；不要塞进后续伤害 / Buff 生效关键帧。
- **主动替换后条件看实际 Buff**：铭文把基础主动替换成专属主动 / 专属 Buff 后，后续击败、受伤、命中等被动条件必须检查新主动实际添加的 BuffID；不要继续沿用基础主动的旧全境守护 / 旧窗口 Buff 条件，否则新链路会漏触发。
- **范围持续效果走 Director / Trigger**：持续区域、旗帜、沼泽、圣焰等优先走 `SkillDirector -> TrapTrigger`，tick 间隔看 `CountdownToRemovalFromWhitelist`，不是 `MaximumEffective`。
- **命中后补逻辑拆被动**：命中叠层、处决、减 CD、追加释放范围等，用被动监听命中/击败/造成伤害事件，并用 `CastConditionID` 限定触发来源 Skill。
- **最低血目标优先走 Skill 搜索字段**：能用 `SearchTargetType + SearchTargetNumber + SearchTargetPriority` 解决时，不新增“受击集合最低血”类 Condition。
- **层数 Buff 自己收尾**：如果需求是“获得 N 层，下次核心技能生效，核心技能释放后移除”，通常让主动 / 被动只负责添加层数，Buff 自身用效果槽事件 `Event_1100000009` 移除自己，避免非核心技能误消耗。
- **多段技能不要把 Event 后当作技能结束**：如果需求是“后续多段都吃按层增伤”，清层不能只挂在“造成伤害后”或“核心技能释放后”。前者会在每段伤害后各触发一次，后者是释放逻辑节点，不保证晚于所有伤害段。优先在主动 `SkillDirector` 最后一段伤害之后补一个末帧 Trigger，关联清理效果。
- **清层要有成功标记保护**：多段技能末帧清 Buff 时，不能无条件清。伤害前条件满足并实际加增伤时先加“本次生效标记”，末帧清层效果必须带“持有本次生效标记”条件；这样未命中、血量条件不满足或没有任何一段真正生效时，不会误清资源型 Buff。
- **新增 Skill 效果必须回查 Director**：主动 Skill 新增效果槽后，要同步确认 `SkillDirector.LogicalTrigger#N.SkillEffects` 引用了新增效果序号。只改 Skill 不改 Director，新增效果不会被主动关键帧执行。
- **helper 改直出 Trap 时别误删 Trigger**：从“释放 helper 再生成范围”改成“主动 Director 直接生成 Trap”时，旧 helper Skill / helper Director 可以废弃；但新主动 Director 引用的 `TrapTrigger` 是有效链路，不能按旧 helper 一起删。
- **寄存结算不读跨 Buff 变量**：能用 `结算寄存-1` 的，结算阶段只填比例和 BuffID；上限、寄存口径放在寄存 Buff 自身。
- **跨窗口增伤用 Buff 层数承载**：不要硬读另一个 Buff 的运行时变量；用可堆叠 Buff 表示层数，效果槽里用按层数计算的属性参数，并用 Condition 限定生效窗口。
- **描述重复时只配一次**：如果主动技能和铭文词条写了同一效果，铭文挂载的 Skill / Buff 只承担实际逻辑或说明载体，不重复配第二套效果。
- **不可直配要降级并写明**：范围内友方数量、跨 Buff 动态变量、复杂受击集合分配等当前字典不稳时，优先给可落表降级方案，并在备注/审核表说明差异。

## §5 易错点与歧义处理

本节不是另一份字典，而是告诉配表 AI 在字典、Excel、proto、运行实现不一致时如何避免静默配错。

1. **先确认载体**：主动关键帧用 Skill Effect；整条被动监听用 Skill.CastEventID；有持续时间、叠层、周期、临时监听或回滚生命周期时用 Buff。被动也可以添加 Buff，选择最短闭环。
2. **Skill Effect EventID 默认不填**：Skill 效果槽里的 EventID 当前不作为订阅入口；只有 Buff Effect 的 EventID 用于订阅事件。不要为了完整给 Skill Effect 补 Event。
3. **概率填引用，不填数值**：`CastChanceID / Effects#N.ChanceID` 填 ProbabilityID；固定概率的 ChanceType 留空，累计概率才显式填类型。100%若必须经过 Event123/Effect1901，使用独立 ProbabilityID=10000。
4. **TargetType 必须按载体解释**：Skill 与 Buff 使用两套枚举，不能照抄；TypeData 内的取值对象、统计对象或锚点不改变最终 Effect 落点。
5. **Effect 槽不能半截**：逐槽检查 Condition、Chance、TypeID、TypeData、TargetType 是否与需求匹配；允许某些 Effect 无 TypeData，但不能留下有参数无 TypeID、或需要目标却没有目标的坏槽。
6. **实例 ID 与类型 ID 分开**：Skill/Buff 引用的是 EventID、ConditionID、ProbabilityID；TypeData 才按对应类型定义填参数。不要把 Condition 参数塞进 EventID。
7. **同类旧配置只能作线索**：字典和旧参考都在持续优化，现有行也可能配错。新配前用当前字典、当前 Excel 字段、proto 和实际 Handler 交叉确认；冲突不得静默选一边。
8. **逻辑复用必须完全等价**：Event/Condition/Probability 只有在类型、参数、顺序、语义和共享意图都一致时才复用；否则默认新增。Condition 最多4个直接项，混合 AND/OR 用隐藏类型99引用子 ConditionID，当前验证最多5层。
9. **Event 上下文决定 Condition 关系**：添加/移除 Buff 时用1000匹配本次 buffID；1001只判断当前持有。造成伤害与受到伤害的 source/target 视角不同，不能只看需求文案里的自身/敌方。
10. **命中次数口径**：Event118按一次 Skill 释放对敌人去重，同一敌人多段只计1次，下次释放重置；Event116按实际攻击生效段触发。
11. **主动 Effect 要回查 Director**：新增或调整 Skill 效果槽后，确认 `SkillDirector.LogicalTrigger#N.SkillEffects` 在正确关键帧引用了该槽；多段结算还要核对顺序。
12. **不要相信 UsedRange**：BattleEvent/BattleCondition 等表可能有残留物理范围。读取实际非空主键并检查末尾；当前 BattleEvent 是102条有效实例。

- [ ] **需求语义**：触发时机、判断对象、最终作用对象、数值来源、生命周期、叠加和移除结果都已唯一化。

- [ ] **Condition**：引用现有 ConditionID 或按完整逻辑新增；AND/OR、顺序和隐藏类型99嵌套已验证。
- [ ] **Chance**：ChanceID 指向正确 ProbabilityID；固定/累计类型填写正确；没有直接把万分比填进ChanceID。
- [ ] **Effect**：TypeID在对应 Skill/Buff 管线有处理器；TypeData每一位均有来源；风险项已显式标注。
- [ ] **TargetType**：按 Skill 或 Buff 的枚举填写；公式取值目标、Buff统计目标、锚点与最终作用对象已分开。
- [ ] **槽位完整**：Skill六槽、Buff五槽全部扫描；没有半截槽，也没有漏掉需要打开的 Buff #2～#5 TargetType。
- [ ] **Buff生命周期**：DurationType/DurationData、自然到期、驱散、顶替、手动移除和 Event订阅结果已核对。
- [ ] **Buff叠加**：当前表只开放 MaxStack；需求可由默认 Rule实现。若必须非默认 Rule，先确认开放精确源表列。
- [ ] **多段/多目标**：118去重与116逐段、20002/70003首条伤害差异、末帧清理顺序已检查。
- [ ] **主动链路**：SkillDirector在正确关键帧引用新增 Effect；Trigger、范围和最后一击顺序可还原。
- [ ] **业务挂载**：上游职业、铭文、词缀、圣物等真实入口确实引用了新增 Skill/Buff/Director。
- [ ] **引用与ID**：所有 ID 存在、无撞号；复用逻辑完全等价，否则默认新增。
- [ ] **源表读取**：按实际非空主键读取，不信旧 UsedRange；备注列和尾部新增行没有漏读。
- [ ] **歧义输出**：凡字典、Excel、proto、运行实现冲突，均标风险/存疑/待验证，没有自行拍板。
