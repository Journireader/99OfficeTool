# 配表执行经验

本文件承接跨系统可复用的配表经验、踩坑和验收方法。它属于源表侧 `配表参考 / 配置表知识库`，用于避免同类配置继续犯错。

这里不记录单次任务过程、临时脚本输出或非项目共用的操作约定；这些内容不应进入项目共用配置表知识库。

## 事实源原则

1. 配表事实、字段语义、ID 规则、跨表引用、I18N 口径、玩家可见文案规则，只维护在源表侧 `配表参考`。
2. 从外部复盘或历史记录吸收内容时，必须改写成项目通用规则；临时路径、临时工具和非共用约定不进入本文。
3. 与源 Excel 或本目录冲突时，以最新源 Excel + 本目录专题为准；历史记录只能作为线索，不能直接当结论。

## 配表前定位

### 先锁主表，再补支撑表

不要从文件名、sheet 名或单个 ID 直接下结论。先回答：

- 主表是哪张 workbook / sheet。
- 这次改的是补行、改值、补字段，还是新结构。
- 是否联动文案、条件、入口、奖励、资源、事件、跳转。
- 是否存在分号列表、同 ID 多行、ID 家族、`GC_*` 条件键或 `NameID` / `DescriptionID` 文案键。

### 摸底要扫全 sheet 字段

一个玩法 workbook 下的横切字段可能分散在多个 sheet。下否定结论前，必须扫该 workbook 全部 sheet 的字段行，尤其是：

- 奖励 / 上限 / 掉落 / 解锁字段。
- `#N` 数组字段。
- `Condition` / `Reward` / `Loot` / `Task` / `Prop` / `Jump` / `Prompt` 相关字段。

“没在主 sheet 找到”不等于“没有这个字段”。

### 业务分类查业务字段

分类、职业、品质、部位、用途等策划内部语义，优先查 `Desc`、备注、Type / Category 等业务字段，不从 I18N 中文名或 ID 段推断。

- 玩家可见文字 -> 查 I18N 对应业务 sheet。
- 业务分类标签 -> 查 `Desc` / 备注 / Type / Category。
- 两个字段都编码同一语义时，优先相信会被跨表引用和程序读取的字段。

## ID 和引用

### 不从 ID 段反推业务语义

ID 段只说明编号规划，不等于业务字段。需要职业、类型、品质、资源层级时，查真实业务字段或最终引用链。

典型禁忌：

- Enemy 职业看 `CareerType`，不要看 EnemyID 前缀。
- Skill / Buff 类型看 `SkillType` / `BuffType`，不要只看 ID 前缀。
- Item / Reward 语义看 `PropType`、`ItemCategory`、`Desc`，不要只看 ItemID。
- Scene / Role / Enemy 表现层判断要追到资源路径，不停在中间 ID。

### 复用 ID 有语义风险

复用现有 `ResId`、IconID、SkillID、ItemID 等引用能少改表，但可能带入原 ID 的旧语义、旧资源、旧数值或旧备注。复用前必须列出：

- 被复用 ID 的原用途和备注。
- 最终运行时实际会读到的资源 / 数值 / 文案。
- 与本次需求不一致的地方。
- 是否接受语义不完全一致，或需要新增专用 ID。

### 表现判断追到底层资源

判断“玩家视觉是否相同 / 是否复用模型 / 是否冲突”时，不要停在 `ResId`、`ModelID`、`IconID` 这类中间字段。

怪物外观典型链路：

```text
Enemy.ResId
  -> RoleRes.xlsx / MonsterRes sheet
  -> MonsterModelID
  -> NudeModel.xlsx / MonsterModel sheet
  -> SpinePath
```

最终以 `SpinePath` 和挂接资源判断表现，不以中间 ID 名称判断。

## I18N 和文案

### I18N 不是分类表

I18N 是玩家可见文案出口，不承载策划内部分类。查物品、敌人、技能的业务分类时，不要用中文展示名反推。

### 文案回填先确认业务 sheet

新增名称、描述、关键词、提示时，不能只写“补 I18N”。要确认落在哪个 I18N sheet，以及主表字段引用哪个 key。

常见路由见：

- `系统/I18N.md`
- `系统/战斗_I18N映射.md`
- `约定/ID编码规范.md`

### 圣物等级描述只改 I18N 正文

圣物等级描述回填时，`RelicBase.RelicDes` 和 `RelicLevel.EffectDes` 存的是 I18N key，不是中文正文。正文回填到 `system/I18N.xlsx#I18N#Relic`。

`RelicLevel.EffectDes` 的 key 应匹配当前行 `Effect` 的首个 SkillID：`Relic_LevelDes_{SkillID}`。设计稿里的注释、开发说明、括号内配置备注不直接进入玩家文案。

## 跨版本和回填

### 按 ID 复核，不按行号复核

源表多人并行时，经常会发生插行、删废行、排序或他人提交后 `svn update`。复核 Skill、Buff、Director、Condition、I18N 时不要沿用上一轮对话或截图里的行号；应先用业务 ID 重新定位：

- Skill：用 SkillID。
- Buff：用 BuffID。
- BattleCondition：用 ConditionID。
- SkillDirector：用 SkillDirectorID，再按 `LogicalTrigger.Type + TriggerID` 找对应 Trigger 子表。
- Inscription：用 InscriptionBuildID，再读 Name / Describe key 和 SkillID。

如果 `svn update` 后本地修改标记消失，说明相关内容可能已被提交或被更新到新版本；必须重新读取当前源表事实，再输出链路或继续修改。

### 回填不只核 ID 集合

从旧产出版、评审副本或历史表回填到当前源表时，不能只核对“ID 是否齐”。还要对齐业务语义字段：

- 类型枚举。
- 备注 / Desc。
- 分类标签。
- 资源层级。
- 当前版本同类样本的字段风格。

推荐做法：选当前源表中同类已生效数据作为“黄金样本”，先列出要对齐的语义字段，再回填旧数据。

### 差集结论要二次验证

引用一致性检查不能只比一个主表。遇到“X 引用了 Y 但 Y 不存在 / Y 没被引用”这类差集时，要继续查：

- 配套 sheet。
- 任务表。
- 条件表。
- 事件表。
- 分号列表和同 ID 多行。

否定结论必须写清是“已全量扫过”还是“当前范围没找到”。

## xlsx 写入边界

### 评审副本和源表回填分开

评审副本面向人工审阅，本次新增或修改单元格标记为黄底、黑字、下划线。

FF 源表回填面向正式配置，不能带评审标记，只写最终值，并保留源表原样式、表头、公式、富文本和无关 sheet。

### 正式源表回填只做最小改动

正式源表回填应从干净基线或回填前备份出发，只做最小范围 value / XML 补丁。任何会重写整个 workbook、worksheet、styles、sharedStrings 或 rels 的做法，都必须先评估格式和打开完整性风险。

### 禁止高层 Excel 库 round-trip 保存 FF 源表

高层 Excel 库读表可以，直接读入后另存 FF 源表风险很高。已知风险包括：

- `.rels` 目标路径被改成绝对路径。
- `numFmts`、`connections.xml`、`definedNames`、`extLst`、图片 / drawing 被丢。
- shared formula 被拆开，引用关系滑动。
- sharedStrings 或 rich text run 被重写。
- Excel 打开出现“部分内容有问题 / 需要修复”。

Excel 修复弹窗属于验收失败。必须从干净基线重做，不能在已污染文件上继续叠补丁。

### 公式门禁

写入前先扫描目标 workbook 的公式：

- 普通公式有非空缓存值时，可以固化为当前缓存值。
- 无缓存值、空缓存值、shared / array / dataTable 等复杂公式必须阻塞。
- 用户要求保留公式时，也要作为风险确认；最终可配置数据区不能残留未确认公式。

证据应包含公式位置、公式类型、缓存值状态和处理策略。

### XML 最小补丁

格式敏感源表新增字段、插列、删行、改单元格值时，优先使用 XML / 字节级最小补丁：

- 只替换目标 sheet 或目标 cell。
- sharedStrings 只追加新条目，不全局替换原字符串。
- 不用 ElementTree 解析再序列化整个 worksheet / sharedStrings。
- 不重写无关 sheet、styles、workbook、rels、media、drawing。

插列前检查 `dimension`、`autoFilter`、`definedName`、`conditionalFormatting`、公式、`mergeCells`、`dataValidations`、`tableParts`、drawing / legacyDrawing、`mc:Ignorable`。

删行时如果 workbook 含 sharedStrings，不能用 openpyxl `delete_rows().save()`；要只删除目标 sheet XML 的目标 `<row>`，并更新必要维度。

### sharedStrings 不做全局替换

同一个 shared string 可能被多个 sheet 共用。只想改某个 sheet 的某个文本时：

1. 找到目标 sheet 的 sheetN.xml。
2. 定位目标列 / 目标格当前 shared string index。
3. 追加新 shared string。
4. 只把目标单元格 `<v>` 改成新 index。
5. 验收目标 sheet 已改，其他 sheet 未变。

### svn xlsx 协作冲突的标准处理流程

xlsx 在 svn 里是二进制，无法做文本级 merge，但业务上仍可以做 ID 级别的三方合并。

**默认权限**：svn checkout 出的 xlsx 默认是 444（只读）。回填前必须 `chmod u+w <file>` 才能写；保存后 svn 会重新锁回只读，不需要手动还原。

**写前必须先确认无人持锁**：444 只读不只是文件系统保护，更是 svn lock-modify-unlock 模型的可见信号——它在提醒"现在有人可能正在改这个文件"。`chmod u+w` 等同于无视这个提醒，跟"偷锁"等价。正确流程：

```
1. svn update <file>                  # 先拿到最新版本
2. svn info <file> | grep 锁定        # 看 server 端 lock 持有者
3a. 若有别人持锁 → 停手；找持有者 svn unlock，或等
3b. 若无人持锁 → svn lock <file>      # 自己拿锁
4. chmod u+w <file>                   # 解除只读
5. 改写、保存
6. svn commit <file> -m "..."         # 自动释放 svn lock + 还原 444
```

**单方 `chmod u+w` + 直接写** 会导致：
- 不知道这期间别人有没有用同一个 lock 在自己工作副本里改 → 提交时 server 拒绝（要么冲突要么"lock not held"），但本地内容已经被覆盖；
- 即使别人没改、提交成功，也违反了团队 lock-modify-unlock 约定，下次别人改这个文件时 svn 不会主动告知"已被某人改了"。

**锁定模型**：xlsx 走 lock-modify-unlock。commit 时若别人正持 lock，svn 会返回 `E195022: 在其他工作副本中被锁定`，错误信息附带 lock 持有者。处理：找持有者 `svn unlock`，或管理员 `svn unlock --force`。`--force` 会让对方下一次 commit 失败被迫 update + 重 lock，慎用。

**冲突标记**：服务端有新版本时本地 commit 失败，需 `svn update`；update 后冲突文件标记为 `C`，并产生两份附加文件：

```
battle/SkillDirector.xlsx        ← 工作副本（含我的改动）
battle/SkillDirector.xlsx.rXXXX  ← BASE（我编辑前的版本，对应我的 svn revision）
battle/SkillDirector.xlsx.rYYYY  ← HEAD（服务端最新版本）
```

二进制无法 textual merge，必须按业务 ID 做三方对比。

**伪 diff 识别**：高层 Excel 库（openpyxl 等）读写 xlsx 时会做语义归一化，最常见的几类"看起来不同、实际等价"：

| 现象 | BASE 单元格 | 工作副本单元格 | 处理 |
|---|---|---|---|
| 空字符串规范成 None | `''` (str) | `None` | 视为相同 |
| 整数被读成浮点 | `1` (int) | `1.0` (float) | 视为相同 |
| 字符串两端空格被 strip | `'abc '` | `'abc'` | 多数视为相同，跨表引用类视为不同 |
| 数字字符串和数字混用 | `'21210000001'` | `21210000001` | 业务上视为相同 |

做 3-way diff 时先用归一化规则过滤伪 diff，再判定真冲突。**真冲突 = HEAD 改的业务 ID 集合 ∩ MINE 改的业务 ID 集合**。

**合并步骤**（已确认有真冲突时）：

1. 备份工作副本（不进 svn）。
2. `cp <file>.rYYYY <file>`（用 HEAD 当新基线，**保留别人的改动**）。
3. 按业务 ID 重新应用我的改动；其它不动。
4. `svn resolve --accept=working <file>` 标记冲突已解决。
5. 重新 commit。

**多文件并行 commit 时**：先把"无冲突 + 无锁定"的文件分组 commit，再单独处理被锁定 / 冲突的文件，降低 commit 全部失败的影响范围。

### 备份命名不进 svn

回填前的 `.bak` 文件留在源表目录里时 svn 会标 `?` (untracked)，不会被 commit。但备份名带中文 + 时间戳容易让 svn 日志输出里出现 unicode 转义乱码（如 `{U+56DE}{U+586B}`），不影响功能但读不友好。推荐英文 + ISO 时间：`SkillDirector.xlsx.bak_pre_backfill_20260528_135330`。

## 产出后自检

每次配表完成后按 4 类扫漏：

| 类别 | 检查 |
|---|---|
| 文案 | I18N Key、Prompt 提示反馈 |
| 接入 | Condition、SystemFunction、Guide、Jump |
| 结算 | Event、SystemEvent、Item、奖励 / 随机池 |
| 资源 | Picture、Audio、SpecialEffect、Window、Avatar、SpinePath 等资源链 |

高风险变更还要补：

- ID 重复 / 越段 / 引用缺失。
- 主键变更后的所有引用表。
- 评审副本标记边界。
- 源表回填 payload 范围。
- Excel 打开完整性。
- 源表锁、版本和提交范围。

## 什么时候不写入本文件

- 单次任务过程。
- 只对某个临时副本有意义的脚本输出。
- 未经源表或专题验证的临时观察。

这些内容可以留在任务包或归档，但不能成为源表侧配表参考结论。
